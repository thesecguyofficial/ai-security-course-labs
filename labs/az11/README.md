# Lab AZ11: secure TSG Helpdesk on Microsoft Foundry: private, Entra-only, customer-managed key, logged

Companion to lessons **11.0 to 11.6** of *AI Security Engineer* (The Sec Guy), Azure stream. About 60 minutes,
**$0**, all on your laptop. **Nothing to install** (Python standard library only) and **no Azure subscription
needed**. An optional Step 8 builds the same setup in your own subscription with Terraform; that one costs money while
it runs, so read its cost section first.

You are still the cloud security engineer at **Contoso** (fictional; "Contoso" is the placeholder name Microsoft uses
in its own documentation). After lab AZ10, keys are off and models are allow-listed. Now Contoso has written
"version 1" of its Terraform for the TSG Helpdesk Foundry resource, and you review it before it ships. In one sitting:

| Part | What you do | Lesson |

| **Break** | Replay 7 attacker and 4 legitimate requests through DNS, network, identity and policy | 11.1, 11.2, 11.5 |
| **Fix** | The same requests against the hardened build in `fixes/` (= `terraform/`) | 11.1 to 11.5 |

**About `foundry_twin.py`.** It is not Azure. It models only what this lab needs, each rule from Microsoft's docs:

- DNS: inside a VNet, `<name>.openai.azure.com`, `<name>.cognitiveservices.azure.com` and
  `<name>.services.ai.azure.com` resolve to the private endpoint only if the matching `privatelink` zone exists, is
  linked to that VNet and is in the endpoint's DNS zone group. Everyone else gets the public address.
- Network: the public endpoint answers only if public network access is enabled and, if `network_acls` defaults to
  `Deny`, the caller's IP is listed. The private endpoint answers callers in its VNet.
- Identity: an Entra ID call needs a role assignment covering the resource whose DataActions match. Roles are read
  from `roles/`, copied from Microsoft.
- Policy: the **real** `policyRule` JSON from `policy-definitions/` and `fixes/policies/` is evaluated by a small
  interpreter (case-insensitive, as Azure Policy is). Deny refuses.

It does not model VNet peering, custom DNS servers, network security groups, Conditional Access, ABAC conditions,
propagation delays, or Azure's exact error bodies. Status codes are "roughly what you'd see". The plans in `contoso/`
and `fixes/` were written by hand in the shape of `terraform show -json`, not generated by Terraform.

**About the data and safety.** Tenant, subscription and object IDs are Microsoft documentation example GUIDs (the same
as lab AZ10); role and policy definition IDs are the real built-in IDs. Public IP addresses are from the documentation
ranges in [RFC 5737](https://www.rfc-editor.org/rfc/rfc5737); VNet addresses are private `10.x`. Every attacker prompt is
labelled LAB PLACEHOLDER; every customer email address is at `example.com`. Nothing here contacts Azure. Test 18 fails if
any of that changes.

## Step 6 · The real KQL

When you have a real gateway, Microsoft's example query joins requests and responses by `CorrelationId`
([LLM logs](https://learn.microsoft.com/en-us/azure/api-management/api-management-howto-llm-logs)). Add the caller
from `ApiManagementGatewayLogs`, and sort the pieces before you join them:

```kusto
ApiManagementGatewayLlmLog
| where isnotempty(RequestMessages)
| order by CorrelationId asc, SequenceNumber asc
| summarize Prompt = strcat_array(make_list(tostring(RequestMessages[0].content)), "") by CorrelationId
| join kind=inner (ApiManagementGatewayLogs | project CorrelationId, CallerIpAddress, TimeGenerated) on CorrelationId
| where not(ipv4_is_in_range(CallerIpAddress, "10.20.0.0/16"))
```

The shape of `RequestMessages` in this lab is simplified. Look at a few of your own rows before you trust any query.

## Step 8 (optional) · The real build, in your own subscription

This deploys `terraform/`: a VNet, a Foundry resource with public access **Disabled** and keys off, a customer-managed
key in a same-region Key Vault with purge protection, a private endpoint with all three privatelink zones, a
Log Analytics workspace with a diagnostic setting, one small `DataZoneStandard` deployment, and a small Linux VM with
no public IP to test from inside. **We have not run this step for you** (this course's build has no Azure
subscription). The Terraform was checked with `tofu fmt`; it was not planned against Azure. Expect to adjust a value
for your region (model availability, VM size).

**Cost.** Unlike lab AZ10, this one has hourly charges while it exists: the private endpoint, the VM and its disk,
plus small amounts for Log Analytics ingestion, Key Vault operations, the DNS zones and a few hundred tokens. We could
not load live prices from Microsoft's pricing pages while writing this lab, so `make cost` lists the meters to look
up for your region in the Azure pricing calculator. Plan a 2-hour session, set a budget alert first (lab AZ10), and run
`make down` the same day. A free account's spending limit stops services when the credit runs out.

```bash
az login
export AZ11_NAME=az11-<initials><4 digits>
export MY_IP=<your public IPv4>
make cost
make up
make cloud-check
make policy
make probe
make logs
make evidence
make down
```

- `az login`: your own subscription
- `AZ11_NAME`: globally unique, lowercase
- `MY_IP`: e.g. from your router; only it may create the key
- `make cost`: what will be billed
- `make up`: terraform plan -> the checker on YOUR plan -> apply (asks first)
- `make cloud-check`: the checker again on cloud-plan.json
- `make policy`: assigns the guardrails incl. YOUR challenge-1 policy; wait 15 minutes
- `make probe`: outside: public address and a refusal; inside: 10.20.2.x and HTTP 200
- `make logs`: what the Foundry resource logged (give it a few minutes)
- `make evidence`: the settings, read back from Azure
- `make down`: removes policies and everything Terraform created

Use OpenTofu instead of Terraform with `export TF=tofu`.

**Step by step, with tests:** `GUIDED-BUILD.md` walks the same build in the portal and with Terraform, then proves
each control with five tests (public path refused, private path logged, wrong identity refused, guardrails hold, key
rotation) and one change that breaks it (a missing DNS link).

Notes:

- `make up` runs the checker on your real plan before asking to apply. Values Terraform only knows after apply (IDs,
  principal IDs) are missing from a plan; the checker follows the plan's references instead.
- If apply fails with 403 on the key or on the customer-managed key, Azure RBAC was still propagating ("can take up to
  5 minutes", Microsoft says): run `make up` again.
- The default model is `gpt-5-mini` 2025-08-07 (GA); `gpt-4.1-mini` is Deprecated and a new subscription can't deploy
  it. If your region doesn't offer the default as `DataZoneStandard`, change `model_name` and `model_version` to a GA
  model it does offer, or to one it offers as `Standard` and set `deployment_sku` to match, in
  `terraform/variables.tf`.
- The probe from inside uses Run Command on the VM and the VM's managed identity: no SSH, no public IP.
- After `make down`, the Key Vault stays soft-deleted for 7 days (purge protection), and its name can't be reused
  until then. Terraform purges the Foundry resource so its name is free again.

## Troubleshooting

| Problem | Fix |
|---|---|
| `python3: command not found` | Install Python 3.11+ from python.org, or use `python` on Windows |
| `make: command not found` (Windows) | Run the `python3 ...` command shown under each step |
| A test fails after you edited `contoso/` | The tests check Contoso **as shipped**. Edit `fixes/` and `hunt.py` only |
| `make challenge` ends with `Error 1` | Expected until you finish the challenge |
| Step 8: `403` creating the key | Your `MY_IP` is wrong, or RBAC is still propagating: check the IP, wait, rerun `make up` |
